# OpenClaw Gateway invariants
<!-- Moved verbatim from CLAUDE.md (2026-09-10). Rule bodies are the SSOT for their domain; CLAUDE.md keeps only the map. -->
OpenClaw is observed over the Gateway WebSocket (live channel) AND its transcript files, and the two carry disjoint
halves. These rules cover subscription, run scoping, the transcript feed, link stability, health frames and the
approval lifetime. Protocol reference: [docs/gateway-protocol.md](../../docs/gateway-protocol.md).

## Subscription, run scope and the transcript feed

- **A Gateway event you never subscribed to is indistinguishable from one the Gateway does not send — and subscribing is not the same as consuming it.** `sessions.subscribe` is a no-param RPC under `operator.read` (the scope `sessions.list` already runs under) and it is the entire admission gate for `session.message` and `session.tool`: a connection in neither subscriber set receives nothing. The Node adapter never called it, so its handlers sat wired and unreachable; the Swift adapter DID call it and then discarded every frame — a different failure and the harder one to see. The only frame arriving was `chat`, and **that frame is assistant-only**: no user prompt, no tool array, no token counts, no model. So nothing emitted a `turn_start`, and a `turn_response` with no open turn is dropped by `Collector.setTurnResponse` — **657 of 665 recorded OpenClaw runs held zero turns**, all closed at ~1800s by the orphan reaper. Three copies of one guess kept it invisible: `ChatEventPayload` declared `prompt`/`tools`/`modelId`, a fixture supplied them, and the parity test read them back — a fixture, a type and an assertion authored together from one assumption agree with each other forever. Fixtures are now **captured off a live Gateway and asserted through the real parser** (`tests/parity/gateway-frames/README.md`). Ownership after the fix, so no fact is counted twice: prompt ← `session.message`(user); tools ← `session.tool` (args AND result, under `data`, never at the top level); per-turn `provider`/`model`/`usage` ← `session.message`(assistant) as a `session_meta` span; response ← both `chat.final` and `session.message`(assistant), deliberately — a run the Gateway hides from the control UI never sends `chat.final`, and the sample layer dedups on `kind|turnIndex|hash(text)`. **`chat.final` is also OpenClaw's stop signal** and emits `turn_end` (`end_source='stop'`; a cancel emits `interrupted`).
- **An OpenClaw APME run is scoped to a session KEY, never to the Gateway connection.** One connection sees every session the agent has — the user's chat (`agent:main:main`), each cron job (`agent:main:cron:<id>`), and a fresh key per model-eval run (a suite opens six in three hours). A connection-scoped run interleaves them into one trajectory under one `model_id` and computes the idle-gap boundary across unrelated conversations, so turn ordering, per-task cost and every judge verdict describe a conversation that never happened. `openclawRunForSessionKey` opens `openclaw:<sessionKey>` lazily on that key's first event and `setApmeRunResolver` hands it to the adapter; **each key owns its own idle-gap timer**, or a heartbeat every few minutes keeps resetting the timer for a chat that ended half an hour ago and the task is never evaluated. `projectName` is the key itself, not the literal "openclaw". A frame with no key falls back to the connection-scoped run — a mis-scoped record beats no record. **A run opens on a span that can RECORD, not on a non-empty span list** (`ApmeCollector.spanCanOpenRun`, kept adjacent to `ingestSpan` because it is a claim about that dispatch): a context is built for every frame including ones that parse to zero spans, so opening it in `apmeEntryFor` manufactured the exact noise the split removes — and the list test that replaced it was the same defect one level down, since an assistant `session.message` always builds a `session_meta` and, with text, a `turn_response`, both of which the collector then discards with no turn open. The four kinds that may open a run are exactly the ones reaching `ingestHook`, which inserts a `steps` row unconditionally. The connection-scoped fallback obeys the same rule and is opened lazily on first use, its id still minted at connect so `hasDirectApmeIngestion` — which gates the bridge's timeline→span conversion — answers unchanged. Measured over the week to 2026-09-09, before the fix: 87 of 113 OpenClaw runs held zero `sample_events` and 82 held zero `steps` as well (25 per-key, 57 connection-scoped), each `_empty`-tagged and held to the 30-minute orphan reaper. Old `openclaw-<uuid>` rows are **not backfilled**; the key was never recorded, so any attribution would be invented.
- **OpenClaw is Gateway-observed AND transcript-observed, and the two carry disjoint halves.** The Gateway WS stream is the live channel (`connect` / `sessions.list` / `chat.send` / `chat.abort` / `exec.approval.*` / — once subscribed — `session.message` / `session.tool`); `bridge/src/openclaw-transcript-timeline.ts` + `openclaw-timeline-feed.ts` read `~/.openclaw/agents/<agent>/sessions/<uuid>.jsonl` and emit **only `tool_exec` rows**, the complement of that stream and never a duplicate of it. **Which producer owns the timeline's tool rows differs per daemon, and that is not an oversight**: Node routes `session.tool` to APME only (its timeline rows come from the transcript feed, so routing both would double-emit), while Swift has no transcript feed — it reaches `~/.openclaw` only through a security-scoped bookmark — so there `session.tool` IS the timeline's source, read from its real `data`-nested shape. Never both at once; one daemon owns the port. Three measured bounds on the feed: only sessions written inside `ACTIVE_WINDOW_MS`; a first sighting emits **nothing** (the opposite of `KiroTimelineFeed` — seeding would inject minutes-old tool calls from finished eval runs); rows attach to the virtual `openclaw-gateway` row rather than minting sessions. **The session key rides every row's `detail`**, or a cron job and a model-eval harness both arrive as the literal "OpenClaw". Gate the feed on `gatewayConnected`, not on the store. Two rules this feed cost to learn: **a producer must be driven by a signal its own subject can move** (`OPENCLAW_FEED_INTERVAL_MS`, not `passiveSessionObserver.onRefreshed` — OpenClaw has no process row, so its turns move nothing that observer sees), and OpenClaw `tool_exec` is carved out of `evictOne` in **both** daemons (it is the only type this feed emits and the first type eviction sheds, so on a full buffer the row evicted itself on insertion; a one-sided carve-out leaves the shared `timeline.json` replay buffers diverged). The `.trajectory.jsonl` is **not** a tool log and **not** an APME enrichment axis — turn boundaries, provider/model and token usage only, all of which now arrive first-hand as `session_meta`. Its one unique field, `gen_ai.system`, has no consumer, so do not cite provider as a reason the transcript is redundant until it is wired to `shared/src/model-provider.ts`. (2026-08-23 — DEVELOPMENT_LOG.)

## Link stability and health

- **A Gateway link that keeps reconnecting reads `connected` at every sample, and the reason it dropped is written only in OpenClaw's own log.** Eleven Gateway restarts in ninety minutes produced eleven `connected` lines, an OpenClaw row flipping to `gateway_not_found` and back on every surface, and nothing that said so — each cycle is indistinguishable from a healthy recovery. `bridge/src/openclaw-gateway-stability.ts` counts disconnects in a ten-minute window (three = unstable), reads the tail of `~/Library/Logs/openclaw/gateway.log` for the sentence OpenClaw prints (`another Gateway owns that state directory` outranks `restart-loop breaker tripped` outranks a routine config restart, whichever is newer), and surfaces it as `gatewayInstability` on `/health` + `/status` plus one `error` timeline row on `openclaw-gateway` — the timeline being the one channel every surface already renders, Android and e-ink included, without a protocol change. Fixtures are the real log lines, not the matcher's regexes. Operator rule the finding points at: `openclaw` on PATH must be `~/.openclaw/bin/openclaw` (the app-installed wrapper running the managed node) ahead of `/opt/homebrew/bin` — two installs fighting over `~/.openclaw/state` is what caused it, and a stray global CLI running `gateway install` bakes `process.execPath` into the plist and recreates the fight. Node daemon only; the sandboxed Swift daemon cannot read the Gateway log. (2026-09-02 — DEVELOPMENT_LOG.)
- **A health frame has three answers, and the third is not "broken".** `gatewayHasError` is the only input that turns the OpenClaw creature SICK and the topology LED red on every surface, and both daemons computed it as `!(payload.ok)` — Node `!(evt.data?.ok)`, Swift `!((payload?["ok"] as? Bool) ?? false)`. A frame carrying no usable `ok` was therefore indistinguishable from a failing one, and the creature stayed sick until the next frame happened to carry one: OpenClaw's health monitor runs on a **300 s** interval (`[health-monitor] started (interval: 300s …)` in its own log), so that window is up to five minutes of a lie. Same shape as the flash-id and `lsof` probes, tilted the alarming way. `resolveGatewayHealth` (`shared/src/gateway-health.ts`, mirrored as `GatewayHealthRules.swift`, both suites replaying `shared/gateway-health-vectors.json`) returns `known:false` for an unreadable frame and the caller **retains** its previous value. The two daemons also disagreed about the payload: the Swift ADAPTER already read a `checks` array and a top-level `status` string, while the Node adapter cast `payload.ok` and dropped the rest — one payload, two verdicts, which is why the rule is shared rather than restated. And the transition is **logged on both daemons**: it was the one flag that could make a creature look broken with no record at all, so a momentary sick crayfish left nothing to diagnose.
